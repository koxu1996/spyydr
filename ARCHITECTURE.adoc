== Core Library Components Analysis

=== Project Structure

**Project Type**: A modular, production-quality web crawler written in Rust +
**Main Components**: Core library (`src/lib.rs`) with CLI binary (`src/bin/main.rs`)

**Directory Structure**:
----
src/
├── lib.rs                    # Main library entry point
├── bin/main.rs              # CLI application entry point
├── components/              # Core crawler components

│   ├── fetcher.rs           # HTTP content fetching
│   ├── frontier.rs          # Task queue management
│   ├── monitor.rs           # Progress monitoring & output

=== Component Details

==== Fetcher (`src/components/fetcher.rs`)
- **Purpose**: HTTP content retrieval with retry logic
- **Implementations**:
  * `ReqwestFetcher`: Production HTTP client with exponential backoff
  * `NoopFetcher`: Testing/development mock
- **Features**:
  * Configurable timeouts, retries, User-Agent
  * Content-Type filtering (only processes `text/html`)
  * Automatic retry on 429 and 5xx errors
  * Returns `FetchedContent` with URL, status code, and body

==== Extractor (`src/components/extractor.rs`)
- **Purpose**: Parse HTML and extract absolute URLs from links
- **Implementation**: `HtmlExtractor` using scraper crate
- **Features**:
  * Extracts `<a href>` attributes from HTML
  * Resolves relative URLs against base URL
  * Filters out non-crawlable links (javascript:, mailto:, tel:, data:, fragments)
  * Returns absolute URLs ready for crawling

==== Canonicalizer (`src/components/canonicalizer.rs`)
- **Purpose**: Normalize URLs to prevent duplicate crawling
- **Implementation**: `QueryCanonicalizer`
- **Features**:
  * Removes query parameters and fragments
  * Can be disabled via configuration
  * Helps reduce duplicate URL processing

==== Policy (`src/components/policy.rs`)
- **Purpose**: Enforce crawling rules and constraints
- **Implementation**: `SimplePolicy`
- **Features**:
  * Maximum depth limiting
  * Domain whitelist/blacklist with suffix matching
  * Case-insensitive domain filtering
  * Rejects URLs without valid hosts

==== Registry (`src/components/registry.rs`)
- **Purpose**: Track discovered and fetched URLs to prevent duplicates
- **Implementation**: `InMemoryRegistry` using `DashMap` for thread-safety
- **Features**:
  * Thread-safe concurrent access
  * Tracks URL status: Discovered → Fetched
  * Bulk registration with filtering of new URLs
  * Status tracking and metrics

==== Frontier (`src/components/frontier.rs`)
- **Purpose**: Task queue management and scheduling
- **Implementation**: `BfsFrontier` using `VecDeque`
- **Features**:
  * FIFO scheduling (breadth-first search)
  * Simple add/pop interface
  * Easily replaceable for different scheduling strategies

==== Monitor (`src/components/monitor.rs`)
- **Purpose**: Progress tracking and output generation
- **Implementations**:
  * `ConsoleMonitor`: Real-time console output
  * `ProgressMonitor`: Periodic statistics reporting
  * `SavingMonitor`: JSON Lines file output
  * `MultiMonitor`: Composite pattern for multiple monitors
- **Features**:
  * Real-time progress reporting
  * JSON Lines export format
  * Extensible monitoring system

=== Orchestration Architecture

==== Engine (`src/orchestration/engine.rs`)
- **Purpose**: System initialization and lifecycle management
- **Features**:
  * Coordinates all components during startup
  * Initializes broker and shared registry
  * Manages system shutdown
  * Provides component access to other parts of the system

==== Agent (`src/orchestration/agent.rs`)
- **Purpose**: Stateless worker that processes crawl tasks
- **Architecture**: Each agent owns instances of: Fetcher, Extractor, Canonicalizer, Policy
- **Process Flow**:
  1. Request task from broker
  2. Fetch content using Fetcher
  3. Extract links using Extractor
  4. Canonicalize URLs using Canonicalizer
  5. Filter URLs using Policy
  6. Register new URLs in shared Registry
  7. Submit new tasks to broker
  8. Report completion

==== Broker (`src/orchestration/broker.rs`)
- **Purpose**: Centralized task distribution using actor pattern
- **Architecture**:
  * `CrawlBrokerService`: Client interface (cloneable)
  * `BrokerWorker`: Single worker thread processing MPSC commands
- **Features**:
  * Thread-safe task distribution
  * Coordinates frontier access
  * Handles task completion events
  * Enforces page limits
  * Monitors system shutdown

== Distributed/Multi-Machine Architecture Potential

The architecture demonstrates excellent **separation of concerns** that would support distributed deployment:

=== Current Multi-Threading Support
- Multiple concurrent agents (workers) within single process
- Thread-safe shared registry using `DashMap`
- Actor-pattern broker for coordination

=== Distributed Extension Points

==== Registry Abstraction
The `Registry` trait could be implemented with:
- Redis/PostgreSQL for shared state across machines
- Distributed consensus for URL deduplication
- Sharding strategies for large-scale crawling

==== Broker Abstraction
Current MPSC channels could be replaced with:
- Message queues (RabbitMQ, Apache Kafka)
- Distributed task queues (Redis, AWS SQS)
- Service mesh communication

==== Frontier Distribution
The `Frontier` trait enables:
- Distributed priority queues
- Site-specific task routing
- Load balancing across machines

==== Component Isolation
Each component is:
- Stateless (except Registry)
- Independently configurable
- Easily mockable for testing

=== Multi-Machine Deployment Strategies

The current architecture's trait-based design enables seamless distributed deployment:

**Registry Distribution**: Replace `InMemoryRegistry` with Redis-based implementation for shared URL state across machines.

**Task Distribution**: Replace MPSC channels in `Broker` with message queues (RabbitMQ/Kafka) for cross-machine task distribution.

**Frontier Scaling**: Implement distributed frontier with site-specific routing and load balancing strategies.

**Component Isolation**: Each component is stateless (except Registry), making horizontal scaling straightforward.

== Key Architectural Strengths

1. **Modularity**: Clean separation of concerns with trait-based interfaces
2. **Testability**: Trait-based design enables easy mocking and unit testing
3. **Concurrency**: Thread-safe design with proper synchronization primitives
4. **Extensibility**: New implementations can be plugged in without changing core logic
5. **Observability**: Comprehensive logging and monitoring capabilities
6. **Graceful Shutdown**: Proper resource cleanup and coordinated shutdown
7. **Error Handling**: Structured error types with retry logic for transient failures

This architecture demonstrates production-quality design patterns that could scale from single-machine crawling to distributed web-scale operations with appropriate infrastructure backends.
